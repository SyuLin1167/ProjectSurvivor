# ProjectSurvivor 開発運用

企画上の基準は [GameDesign.md](GameDesign.md) v0.1。本文は管理方針であり、ゲーム仕様を上書きしない。

## 共有元

- [管理Project](https://github.com/users/SyuLin1167/projects/2)
- [Issues](https://github.com/SyuLin1167/ProjectSurvivor/issues): 目的・範囲・完了条件・依存関係・検証結果・判断記録
- PR: 差分・検証・レビュー。GitHubを進捗の共有元とし、チャットだけで完了扱いにしない。
- [未確定事項](SpecificationDecisions.md) / [初期調査と計画](ProjectPlan.md)

## ステータスと着手順

| Status | 条件 |
|---|---|
| Backlog | 計画済み。依存や将来の仕様確認が未完了 |
| Ready | 依存先完了・必要な仕様承認・作業範囲・検証方法が明確。判断整理Issueは提案作成に着手可能 |
| In Progress | 担当が着手を宣言し調査/実装中。原則、開発担当1人につき1件 |
| In Review | 成果と検証結果を提出しレビュー中。実装IssueはPRをリンク |
| Blocked | 具体的な障害や判断待ちで進めない。理由・影響・解除条件・回答者/依存Issueを記録 |
| Done | 完了条件を検証済み。実装/文書変更はユーザー承認のうえPRマージ済み。判断Issueは回答記録済み |

優先度: P0=次段階の成立に不可欠・進行を止める問題、P1=MVP品質/評価に必要、P2=承認済み範囲の後回し可能な改善。優先度は仕様の確定度を意味しない。
Phase 0〜4はGameDesign §7に一致させる。Readyから優先度、依存順、Phaseの順で選ぶ。最初は #1、次に #2。#3は企画判断の整理であり、回答を得る前にPhase 1実装へ進まない。

## 開発担当の標準手順

1. GameDesign、AGENTS.md、対象Issue、関連PR、Projectを読む。ブランチ/未コミット差分を確認し、他人の変更を上書きしない。
2. Issueに着手宣言（担当Work/ブランチ、範囲、再利用候補、検証予定）を残しIn Progressへ。人間のGitHubアカウントを勝手に担当者にしない。
3. 最新mainからIssue単位のブランチ（例: issue/1-baseline）を作る。関連コードを調べ、既存基盤の再利用を優先。新しいクラスや抽象化は必要性と調査結果に基づいて選ぶ。
4. 未確定事項が実装に影響するなら、選択肢・推奨・影響をIssueに記録し企画担当に確認する。回答までは依存部分をBlockedとし、独立した承認済み作業だけ継続する。
5. 範囲内で最小変更。無関係な整形/リネーム/基盤置換を混ぜない。追加問題は別Issueへ。
6. 対象構成でビルドし、Issueの完了条件に沿って動作を検証。環境・コミット・構成・手順・期待/実際・ログ/画像・未実施理由を報告する。静的確認だけで実行確認済みと書かない。
7. PRに対象Issueを Closes #番号 で関連付け、問題/変更後の挙動/再利用点/検証/残課題を記す。未完成はDraft。レビュー可能ならIn Review。
8. 指摘を修正して必要範囲を再検証。PRマージはユーザーの明示承認が必要。承認なしの自動マージ設定や直接main更新は行わない。
9. マージと完了条件を確認してDone、IssueをClose。マージなしでPRがCloseされた場合はDoneにしない。調査/判断のみのIssueは成果や回答が受理されてからClose。

## 自律管理と承認境界

管理担当は既存Issue/PRを確認して重複を避け、日常の分割・優先度・状態・依存リンク・ブロッカーを更新できる。定期監視の自動実行はこの文書だけでは開始されない。
ユーザー承認が必要: 重要な仕様変更、大規模設計変更、既存コードの大規模削除、PRマージ、大幅な開発スコープ変更。
仕様承認は回答リンク・承認者・日付・対象Phase/Issue・試作限定か正式かを残す。正式仕様の変更はGameDesignへの変更PRを提案する。

## 依存・ブロッカー・進捗更新

- Issue本文の依存番号を正本とする。追加の依存は双方にリンクし循環がないか確認する。PRは対象Issueにリンクする。
- Blockedには「原因 / 必要な回答・作業 / 解除条件 / 担当窓口 / 次回確認の契機」を記載する。解除後、残依存と承認を再確認してReadyに戻す。
- 着手、障害発生、PR作成、検証結果変更、承認回答、マージ、Phase完了を更新契機とする。PR作成だけでDoneにしない。
- 自動ワークフローは補助。Issue close/PR merge後も完了条件を照合し、重複・中止は成果として数えない。
- Phase完了報告には達成条件、対象Issue/PR、検証結果、未確定事項、残不具合、次にReadyとなるタスクを含める。

## Project設定（2026-10-15確認）

- Status: Backlog / Ready / In Progress / In Review / Blocked / Done。
- Phase: Phase 0〜4、Priority: P0/P1/P2。各Issueにも分類を記載する。
- タスク一覧とステータス別ボードを使用する。
- 対象リポジトリのopenなIssues/PRを自動追加し、追加時はBacklog。
- PRがIssueにリンクされた場合のIn Progressと、PRマージ後のDoneは補助的な自動更新。In Reviewへの移動とIssueの完了条件確認は管理担当が行う。
- Auto-close issue、Item closed→Doneは無効。中止・重複・未マージCloseを開発完了と誤認しない。
