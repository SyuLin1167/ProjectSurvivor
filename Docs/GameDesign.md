# ProjectSurvivor 企画書・MVP仕様書

**Version:** 0.1  
**Status:** MVP企画整理  
**Project:** ProjectSurvivor  
**基盤:** 2DGameSample（C++ / DxLib）

---

## 1. プロジェクト概要

### 1.1 ゲームコンセプト

**「進み続ける拠点を守りながら、戦い、探索し、追いかける2Dアクションゲーム」**

本作は、Vampire Survivors系の大量敵戦闘を参考にしつつ、移動する防衛対象を取り入れた2Dゲームである。

プレイヤーは自動で進み続ける拠点を護衛し、接近する敵を撃退する。

拠点はプレイヤーを待たない。プレイヤーが離れすぎた場合でも拠点は前進し続けるが、プレイヤーは移動によって追いつくことができる。

この仕組みにより、拠点周辺での防衛と、拠点から離れて行動するリスクの間に判断を生み出す。

### 1.2 開発目的

本プロジェクトには以下の目的がある。

- 2DGameSampleを活用したゲーム開発の実践
- AI主導の開発ワークフローの検証
- 既存のコンポーネント設計やゲーム基盤の実用性確認
- ゲーム性と技術的挑戦を両立した作品制作
- ポートフォリオに利用できる成果物の作成

### 1.3 開発方針

- 初期開発は単一のメインAIエージェントを使用する
- 既存基盤をできるだけ再利用する
- 必要性が明確になるまで過度な抽象化を避ける
- 小さなプロトタイプから段階的に開発する
- 仕様の不明点は推測で確定せず、企画担当へ確認する

## 2. 確定している基本仕様

### 2.1 移動拠点

- 拠点は常に自動移動する
- プレイヤーが離れていても停止しない
- プレイヤーを置き去りにすることがある
- プレイヤーは後から拠点に追いつける

### 2.2 プレイヤー

- プレイヤーは拠点とは独立して移動できる
- 拠点から離れて行動できる
- 拠点を追いかけて合流できる

### 2.3 ゲームの方向性

- 移動拠点の防衛を中心とする
- アクション性と状況判断を重視する
- ゲーム性だけでなく実装上の技術的挑戦も評価する

---

## 3. 基本ゲームループ

以下はMVPで検証するゲームループの案である。

1. 拠点とプレイヤーがステージに出現する
2. 拠点が自動的に前進する
3. 敵が出現し、プレイヤーや拠点に接近する
4. プレイヤーが敵を撃退し、拠点を防衛する
5. プレイヤーが拠点との距離を調整しながら戦う
6. 一定距離または一定時間の防衛成功でクリアとなる

拠点が破壊された場合はゲームオーバーとなる設計を暫定案とする。

---

## 4. 本作の独自要素

### 4.1 プレイヤーを待たない拠点

一般的な固定拠点防衛とは異なり、防衛対象そのものが移動する。

プレイヤーは敵を倒すだけではなく、拠点との位置関係にも注意を払う必要がある。

### 4.2 離脱と合流

拠点から離れて敵を迎撃したり、戦いやすい位置を取ったりできる。

しかし、離れている間も拠点は進み続ける。

離脱する自由と、合流する必要性の両方が存在する。

### 4.3 移動する戦闘エリア

拠点の移動に伴い、敵との遭遇位置やプレイヤーの防衛位置が変化する。

固定された場所で戦うだけではない戦闘体験を目指す。

## 5. MVP仕様

### 5.1 MVPの目標

**「移動拠点を守りながら戦うこと自体が面白いか」を検証する。**

MVPでは演出やコンテンツ量よりも、拠点とプレイヤーの位置関係からゲーム性が成立するかを重視する。

### 5.2 最小構成案

| 要素 | MVP仕様案 |
|---|---|
| ステージ | 1種類の仮ステージ |
| プレイヤー | 8方向移動 |
| 拠点 | 一定速度で自動前進 |
| プレイヤー攻撃 | 1種類 |
| 敵 | 基本敵1種類 |
| 敵AI | 対象へ接近する単純なAI |
| 拠点HP | あり |
| 勝利条件 | 一定距離の移動完了 |
| 敗北条件 | 拠点HPが0になる |
| 表示 | 拠点HP、進行状況 |

※上表は**実装を始めるための暫定提案**であり、正式決定ではない。

### 5.3 MVPで実装しない要素

- 複数ステージ
- 大量の武器や敵のバリエーション
- 複雑な成長・ビルドシステム
- 永続アップグレード
- 本格的なグラフィック・演出
- オンライン機能
- 複雑な経路探索
- 大規模な自動生成マップ

## 6. 技術的検証項目

### 6.1 自動移動拠点

プレイヤーとは独立した更新処理で拠点を動作させる。

検証項目：

- フレームレートに依存しない移動
- 移動中の当たり判定
- 拠点HP管理
- プレイヤーとの位置関係

### 6.2 プレイヤーと拠点の距離管理

プレイヤーが拠点から離れ、再度追いつけることを確認する。

検証項目：

- 拠点とプレイヤーの相対位置
- カメラ制御
- 画面外オブジェクトの扱い
- 長距離移動時の挙動

### 6.3 敵AIとターゲット管理

敵がプレイヤーまたは拠点を攻撃する仕組みを検証する。

検証項目：

- ターゲット選択
- 移動対象の追跡
- 接触・攻撃判定
- 敵オブジェクトの生成と破棄

### 6.4 既存基盤との統合

2DGameSampleの既存機能を優先して利用する。

主な確認対象：

- オブジェクト管理
- コンポーネント管理
- 当たり判定
- 描画・アニメーション
- 入力管理
- リソース管理
- シーン遷移

既存コードの詳細を確認する前に、新規クラスやシステム構成を確定しない。

## 7. AI開発向けタスク

### Phase 0：基盤調査

**目的：既存コードの構造を把握する**

- 2DGameSample由来の機能を調査
- 再利用可能な機能を特定
- 不足機能を洗い出す
- 実装方針を提案する

完了条件：
既存機能、追加が必要な機能、推奨実装順序を説明できる。

### Phase 1：移動プロトタイプ

**目的：拠点との位置関係を検証する**

- 仮プレイヤーを配置
- プレイヤー移動を実装
- 自動移動拠点を配置
- カメラ制御を実装
- 拠点への追いつき動作を検証

完了条件：
拠点がプレイヤーを待たずに進み、プレイヤーが自由に離脱・再合流できる。

### Phase 2：戦闘プロトタイプ

**目的：防衛アクションを成立させる**

- 敵の生成
- 敵の移動AI
- プレイヤー攻撃
- ダメージ処理
- 拠点HP管理

完了条件：
敵が接近し、プレイヤーが敵を倒すことで拠点を守れる。

### Phase 3：ゲームループ構築

**目的：短いゲームとして成立させる**

- ゲーム開始処理
- 敵の継続出現
- 拠点進行状況の管理
- クリア・ゲームオーバー
- 最低限のHUD

完了条件：
ゲーム開始から終了まで一通りプレイできる。

### Phase 4：検証・調整

**目的：ゲーム性を評価する**

- 拠点速度の調整
- プレイヤー速度の調整
- 敵の出現頻度・移動速度の調整
- 拠点から離れることの利点と危険性を確認
- 不具合修正

完了条件：
移動拠点防衛のゲーム性を評価でき、次の開発方針を判断できる。

## 9. 開発担当AIへの運用ルール

1. 本書を企画上の基準資料として使用する。
2. 確定仕様と暫定提案を区別する。
3. 実装前に既存コードを調査する。
4. 既存基盤を再利用し、不必要な重複実装を避ける。
5. 大規模な設計変更は実装前に相談する。
6. 未確定事項が実装に影響する場合は企画担当へ確認する。
7. 各Phaseの完了時に実装内容と検証結果を報告する。
8. 仕様変更が生じた場合は本書への反映を提案する。

## 10. 今後の企画方針

最初は最小限の防衛ゲームを成立させ、そのプレイ結果から追加要素を判断する。

特に重視する評価項目は以下の3点。

- 拠点が動き続けることが、面白い判断を生んでいるか
- 拠点から離れて行動することに意味があるか
- プレイヤーが拠点に追いつける仕組みが、ゲーム体験を豊かにしているか

これらが成立した段階で、成長、探索、拠点強化、敵の多様化などを検討する。

**本企画の最優先事項は、機能を増やすことではなく、「移動する拠点を守る」という独自のゲーム体験を成立させることである。**
